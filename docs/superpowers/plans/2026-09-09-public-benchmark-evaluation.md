# Silicon Notebook 公开 Benchmark 持续评测计划

> 状态：2026-09-09 用户授权执行；2026-09-10 用户暂停具体运行，转回项目设计。400 次 Ask 已完成，baseline judge 部分完成，smoke 流程已验收；人工校准与完整 baseline 未完成。每周 timer 已停用。当前事实见 [执行记录](../../public-benchmark-execution.md)，后续建议见 [开发路线讨论稿](../../development-roadmap.md)。未完成项目不得自动继续。
> 执行时使用 `superpowers:executing-plans` 按下列任务推进；数据与模型调用仅在隔离评测目录运行，生产代码和配置不修改。

**Goal:** 用公开 benchmark 为 Silicon Notebook 的文档问答建立可重复运行、可解释回归、可验证修复的评测闭环。

**Architecture:** 从产品的文档检索、事实回答、数值推理和引用能力出发，优先采用 DeepEval 内置的 SQuAD 和 DROP 数据。原文进入隔离 notebook，问题进入原生 Ask；真实输出进入 DeepEval 与确定性检查，形成版本化结果及逐问题比较。

**Tech Stack:** Silicon Notebook 原生导入、索引和 Ask；Python；DeepEval；公开数据原始结构；JSONL/JSON/Markdown 本地产物。

**Spec:** 本轮用户要求以被测产品和 DeepEval 能力为设计依据；[评测上下文](../../evaluation-context.md)规定实验事实、人工判断和假设分层。现有试验只用作实施阶段的环境与接入参考。

## 1. 首版范围

首版回答四个问题：系统能否找到证据，能否答对，答案是否有可靠引用，以及 reasoning 的质量收益是否值得额外成本。

| 被测能力 | 场景 | 主信号 |
| --- | --- | --- |
| 文档事实问答 | SQuAD 原文中的事实提取 | 答案正确性、证据覆盖、忠实性 |
| 基于文本的数值与多步推理 | DROP 的计数、数值运算、日期与文本答案 | 答案正确性、必要信息覆盖、推理结论支持 |
| 两种产品问答模式 | 同一问题分别调用 chunk / reasoning | 逐问题质量差异、延迟、模型调用与 token |
| 引用可追溯性 | 产品原生回答与引用对象 | 引用目标存在性、声明与证据支持关系 |
| 持续回归 | 固定问题、语料和指标，比较两个系统版本 | 回归样本、错误分桶、校准后的决策 |

本轮使用文本来源，覆盖原生导入后的问答链路；不据此评价 PDF/OCR、表格和公式解析。多轮、KG 构建质量、专门的重排消融、来源权限、深度报告和 UI 不属于首版验收范围。

首版比较无预建 KG 的 chunk 和 reasoning：产品 reasoning 可在无图时工作。必须记录实际触发的分支，不能把两种模式的差异描述为纯推理模型差异，也不能据此推断有图路径的表现。

## 2. 数据选择与使用方式

### 2.1 首版必做

| 数据 | 为什么选择 | 具体使用 | 限制 |
| --- | --- | --- | --- |
| SQuAD | 问题、段落、参考答案与答案位置可以对应，适合来源驱动的事实问答 | 100 个问题，保留原始段落及答案位置 | 内置实现加载 SQuAD 1.x，不包含 2.0 的不可回答任务 |
| DROP | 根据段落回答数值、日期和文本问题，适合工程问答中的信息组合与运算能力诊断 | 100 个问题，保留所有官方可接受答案及答案类型 | 主题主要不是半导体；答案标注不等于完整推理证据标注 |

两者均有 DeepEval 内置 benchmark 实现。首版评测对象是 Silicon Notebook，使用的是这些公开数据对应的产品问答任务。

DeepEval 原生执行通常直接向模型提供阅读材料及问题。将整个原生提示传给 Ask 会让材料出现在用户问题里，不能据此证明产品完成了检索。因此主评测从上游结构化字段取材料和问题，不反向解析 few-shot 提示：只导入原文，只向 Ask 提交问题；参考答案仅进入评分阶段。

报告命名为“基于 SQuAD / DROP 的 Silicon Notebook 评测”。它是改编后的产品任务，不冒充原始排行榜成绩。原生 benchmark 的模型评测可在排查生成问题时作为额外对照，不是首版必须完成的另一套大型运行。

### 2.2 固定样本与候选文档

- 每集从官方 validation split 选择 100 个不同原始段落，每段固定 1 个问题；SQuAD 覆盖不同文章主题，DROP 按答案类型分层。
- 每集分为 20 个调试问题、80 个固定回归问题。按原始文章或段落组隔离，相关段落、重复问题与等价改写不跨组；若组约束导致无法恰好满足配额，以无泄漏为先，冻结前在 manifest 中明确实际数量。
- 每集另外固定 100 个未被选为问题证据的不同原始段落作为干扰文档，来自同一官方 split。它们只是未标注为本题证据的候选，不能直接认定全部无关。
- 每集建立一个固定候选库，目标约 200 个段落来源。原始段落作为独立 Markdown source，保存原始标题和段落 ID；这不代表完整 Wikipedia 文章或完整官方检索语料库。
- 抽样算法、分层配额、随机种子建议值 `20260909`、最终问题 ID、原文哈希和候选库清单全部冻结；不能根据系统是否答对来选择或替换样本。
- 原文仍按产品原生规则切块，使用已记录的来源范围与索引。两种模式共享相同的文档集合和模型配置，分别建立独立运行状态。

这个设计选择的是固定 notebook 范围下的文档问答，不要求先做全库压力测试。后续扩大候选库属于另一个实验配置，需要单独报告。

### 2.3 后续扩展

| 优先顺序 | 扩展 | 进入条件 |
| --- | --- | --- |
| 1 | BoolQ 的证据判断问题 | 首版稳定，补充 Yes/No 任务；No 不等于拒答 |
| 2 | 中文公开问答与 EDA Corpus-QA | 审计参考答案、来源映射和文档版本，建立独立领域分桶 |
| 3 | 不可回答问题 | 加载适合的数据或人工核验派生样本；不能将检索失败自动标为不可回答 |
| 4 | 跨文档多跳、长文档、KG 与引用专项 | 现有分桶暴露明确覆盖缺口，再选择 MultiHop-RAG 等数据 |
| 5 | IFEval 等回答约束专项 | 选择与产品契约兼容的约束；与问答正确性分别报告 |

这些扩展不拖延首版闭环。模型生成的补充样本只作为候选；公开参考答案不改写为模型自生成答案。

## 3. 执行与观测协议

```text
版本化公开原文 -> 隔离 notebook -> 原生导入、切块与索引
版本化问题 ------------------> chunk / reasoning 原生 Ask
                                  |
                      答案、真实上下文、引用、轨迹、耗时
                                  |
               DeepEval 语义评分 + 确定性检查 + 人工校准
                                  |
                      baseline -> 变更比较 -> 修复验证
```

每个问题保持独立会话；关闭或隔离会造成跨题污染的 Memory、回答偏好和检索经验状态，配置事实写入 manifest。隔离数据库、来源文件、索引、缓存和两类日志；不改生产配置与生产代码。

必须核对评测用户的有效文档数量上限，通过产品支持的评测环境配置满足候选库规模，不能绕过导入限制或偷偷缩小语料。

结果协议至少包含以下字段，具体序列化在实施时沿用现有项目风格：

| 类别 | 内容 |
| --- | --- |
| 数据身份 | dataset/version/split、question_id、passage_id、原始问题、references、标注类型、抽样分组 |
| 证据映射 | 公共段落 ID -> source_id -> chunk/element IDs；有原始位置标注时保存位置及文本校验结果 |
| 产品输出 | 原生 answer、mode、实际来源范围、引用、model_errors、明确的失败状态 |
| 生成输入 | 原样的上下文文本、按实际顺序排列的片段、对应 IDs 与每次合成调用关联 |
| 检索观测 | 可采集的候选与最终证据列表、所处阶段、顺序语义、实际数量；未采集阶段明确缺失 |
| reasoning | 真实计划、检索动作、反思和合成阶段的产品可观测轨迹；不把模拟轨迹算作运行事实 |
| 运行记录 | 代码与依赖版本、模型角色、prompt/配置哈希、索引版本、缓存状态、耗时及 usage |

`retrieval_context` 必须来自真实合成输入，不能用 gold evidence 替代。若 reasoning 存在多次合成，保留各次调用与输出归属；不要把最终回答从未见过的证据拼成一个“实际上下文”。无法确认上下文归属的指标记为不适用，不伪造输入。

## 4. 指标与解释

### 4.1 首版评分组合

| 指标 | 定义及用途 | 执行范围 |
| --- | --- | --- |
| Answer Correctness，使用 GEval | 依据问题和官方参考答案，判断结论正确、必要信息完整、无矛盾；接受等价表达 | 全部有效回答；每集独立评分规则 |
| Faithfulness | 回答中的事实是否受到本次实际上下文支持 | 实际上下文可以正确采集的回答 |
| Answer Relevancy | 是否回应原问题及其限定条件 | 全部有效回答 |
| Contextual Recall / Precision / Relevancy | 观察答案相关信息覆盖、上下文排序及噪声 | 调试集与预先固定的诊断子集，先验证适用性 |
| 段落命中与覆盖 | 公共段落映射在实际检索/最终上下文中是否出现 | 有确定性映射的样本，按阶段分别计算 |
| 引用有效性 | 引用对象存在、位于本次授权范围、可以定位到原文 | 全部回答；引用支持另做人工校准的语义判断 |
| 延迟与成本 | Ask 墙钟时间、模型调用次数、token、重试与实际可得的费用 | 全部尝试；导入、索引和 judge 开销分别记录 |

正确性评分规则冻结为：识别问题要求的事实或数值，比较所有适用参考答案，检查遗漏和矛盾。数值、日期、单位及问法限定是必要信息，不能仅因主题相同判为正确。DROP 的计算结论允许基于材料中的操作数进行有效推导；人工校准必须覆盖这种情况，避免把合理运算误判成无证据声明。

不把上述分数加权成单一产品总分。首版主报告分别展示正确性、忠实性、证据覆盖、引用、执行成功率与成本。

### 4.2 必须保留的口径边界

- SQuAD 的原始答案位置可用于检查答案证据是否进入实际片段。只命中文档不能证明答案所在片段被送入模型。
- DROP 默认只做原始段落级命中检查。没有人工核验的必要操作数或推理证据标注时，不报告“完整推理证据召回率”。
- 若有真实排序列表，可报告去重段落级 Hit/Recall/MRR@5、@10，先去重再截取；不足 K 如实记录。两种模式若不暴露可比排序，优先比较最终上下文证据覆盖，不强行制作统一排名。
- SQuAD 的单段正例上，段落级 Hit 与 Recall 信息基本重复。多项名称不能被解释为多份独立质量证据。
- Contextual Recall 基于参考答案文本判断支持性；短实体答案和 DROP 数值答案可能不能表达完整证据需求。因此它是诊断指标，不能代替证据标注与正确性。
- DeepEval 内置 SQuAD 使用 LLM judge，DROP/BoolQ 有特定答案格式要求。产品的长回答含解释与引用，不能直接用整段回答执行严格字符串匹配，再称其为原任务准确率。
- 引用对象存在不等于语义正确；Faithfulness 高也不等于所有关键结论都有正确引用。
- 无回答、产品错误与 judge 错误分别记录；judge 缺失不填零。报告各指标应评数、有效数、跳过数、失败数，不能只展示成功样本均值。

## 5. 人工校准与比较规则

1. 从调试集固定选择两集各 10 题，覆盖不同题型；核查两种模式共 40 份答案、实际证据与引用。先给人工标签，再查看 judge 理由，减少锚定偏差。
2. 正确性、忠实性与引用支持分别标记“符合 / 部分符合 / 不符合”，另记“无法判断”。分歧样本由第二位评审复核，不将无法判断强行折算为分数。
3. 同一份保存输出使用相同 judge 独立评分至少两次；重复性检查绕过评分及模型响应缓存。它测 judge 波动，不冒充产品生成稳定性。
4. 单独对固定的小组问题重跑产品，观察生成和检索波动；与上述固定输出重评分分开记录。
5. 冻结 judge 模型、版本标识、参数、rubric 与指标版本。模型与 judge 尽量使用不同模型；若只能共用，则在报告注明共同偏差，并保留人工判断。
6. 回归比较只在问题、语料与评分协议一致时成立。改变 judge 后，对保存的 baseline 和候选输出一起重评，生成新的评分版本。
7. 报告逐问题差值、各分桶均值、有效覆盖率与配对不确定性区间；按原始文章/段落组考虑样本相关性。80 题级别的小回归集不支持对微小分差作强结论。

调试集用于修改评分规则与参数；固定回归集用于变更比较。持续查看和使用的回归集不称为永久独立最终测试集，后续对外结论需要另设未用于调参的保留集。

任务规模按可验收产物划分，不以既有试验完成度跳过验收。

### 任务二：接入两种产品模式

- [x] 保存所有尝试及错误；已完成输出可被单独评分，无需重新调用产品。

计划涉及：新增 `src/rag_eval/system_capture.py`、`scripts/run_public_benchmark.py`；复用 `protocol.py`、`artifacts.py`。参考已有实验的隔离方法，不直接继承其固定数据集和 chunk-only 限制。

验收：原文不在用户问题里；两个模式确实执行；上下文采集符合第 3 节；所有可变运行路径都位于评测目录；产品代码与生产状态不变。

### 任务三：评分与人工校准

- [ ] 输出调试集报告及建议阈值的依据。尚不能稳定判断的语义指标继续只作观察。

验收：评分缺失不会被当作成功或低分；数值等价、否定、遗漏和引用错误的代表性案例经过核验；无未经校准的硬门禁。

### 任务四：建立固定 baseline 与变更比较

- [x] 对每集 80 个固定回归问题执行两种模式。加上调试集，首轮计划共 200 个独立问题、400 份产品输出，校准重跑另计。

- [ ] 当有实际优化候选时，用相同协议比较并核验修复；首版不为制造优化案例而修改产品。

验收：每个结论可追溯到问题、证据与配置；基线结果不可被后续运行覆盖；版本不兼容会阻止误比较。

### 任务五：接入持续运行

- [ ] 先从固定回归集预选 20 个问题运行集成 smoke，两种模式共 40 次 Ask；它仍是在线集成评测，不能冒充离线单元测试。
- [ ] 首版质量结果采用告警和人工判断；数据损坏、隔离失败或产物缺失使评测任务失败，不将其误报为产品质量下降。
- [ ] 完成人工校准与多次同配置重复运行后，另行固化分桶阈值、容忍区间和失败覆盖规则，再决定是否成为发布门禁。

计划涉及：评测项目自己的调度入口与运行配置；更新 `README.md`、`docs/evaluation-status.md` 和结果索引。当前评测目录没有独立 Git 仓库，实施时先确定版本托管与 CI 归属；本地受控定时任务也可完成自动运行，不把云平台账户作为前置条件。

验收：一次自动触发能完整产出结果与差异报告；一次失败有明确状态且可审计；没有把示例阈值当成产品发布契约。

## 7. 工件、成本与完成定义

每轮使用新的 `var/public-benchmark/<run-id>/`，包含 `manifest.json`、`questions.jsonl`、`document-map.json`、`attempts.jsonl`、`outputs.jsonl`、`scores.jsonl`、`summary.json`、`report.md`、源码与依赖快照，以及隔离运行时。人工标签作为独立、版本化文件保存。

下载与语料导入只保留实验需要的副本；模型服务地址和密钥不进入公共报告。评测结果默认保存在本地，Confident AI 的上传与协作功能不是必要依赖。

费用按导入/embedding、产品问答、judge、人工核验分别估算。先用任务二的调试小样本测量 token 和耗时，再外推本轮工作量；不使用此前不同数据集的耗时直接给出预算承诺。无法获得 provider usage 时记为未知，估算费用注明单价来源与日期。

不人为添加外层运行时限。预算控制通过运行前选定样本和指标实现，不在运行中删减真实上下文。保留底层请求超时与重试配置、失败首次尝试和后续恢复记录，不静默重评已有失败分数。

首版完成意味着：固定公开数据和两种原生模式均可运行；有经过人工核查的主指标；每个失败可解释和重放；有 baseline、版本比较与自动触发任务。它证明的是这批英文文本问答任务上的持续评测能力，不等于 Silicon Notebook 全产品或半导体领域质量已经通过认证。
