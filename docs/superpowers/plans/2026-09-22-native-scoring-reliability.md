# 原生评分故障恢复

目标：服务器已保存 SN 回答，但评分被超时阻塞。让单项完成立即保存、可以只评一个指标，以及对已保存组件补评；不改评分算法、不重造轨迹、不修改 SN。

已核实：DeepEval 4.2.2 原生同步 iterator 先评请求级指标再遍历 span；多查询另走 evaluate。ContextualRelevancy 会逐段调用 judge 后生成理由。SDK 累计任务时限和网关单请求时限不同。当前没有 native-scores 不能证明每个指标都尝试过。

实现顺序：

1. 用真实 SDK + 假 judge 证明：前项成功后，后项开始/中断之前，前项分数已经 fsync。使用公开 BaseMetric 包装内置 measure，仅增加落盘和调用关联，不改模板、分数或 SDK 私有字段。
2. 原生入口增加显式指标选择；未选指标不产生假 N/A。保留原生 trace/span 挂接。SDK 调度不修改；服务器以独立命令先组件、后轨迹。
3. 新增已保存组件评分入口：严格选择 sample_id 和组件指标，使用公开 LLMTestCase/evaluate。只读来源、新目录存放来源哈希、样本、配置、逐项事件、分数。无 notebook 导入或 Ask；不支持 JSON 整轨迹回放。
4. judge 事件增加逻辑调用耗时、评分关联 ID、安全的 HTTP status/错误类型；重试和请求时限继续来自显式 judge 配置。记录 SDK 有效任务时限，允许命令显式设置。不宣称逻辑调用等于 HTTP 尝试。
5. 定向回归后执行相关离线全量一次，更新交接。服务器先一个检索样本和一个 reasoning 合成样本，保留完整输入，max_retries=0；不扩到 meeting18 其余题，直到链路可行。

失败语义：已保存的成功/错误结果唯一；未开始与中断写明原因，分数 null。SIGKILL 时 started 无终态表示未完成，不能推断 0/N/A。旧答案/组件/客观分及已成功 Agent 分保留。不同 judge、输入、配置批次不混算。单次 504 只证明该次未按时返回，不证明某模型一定无法评分。

边界：此次不修改 SN 补丁、Dashboard、benchmark 数据、指标算法或完整轨迹内容。本地不访问在线模型、不下载数据。服务器仍需验证真实延迟。

实施结果：已完成上述入口与持久化；432 项离线测试通过，网络尝试 0。审阅补充发现 SDK 同步任务超时不会停止工作线程，已修复逐任务及时固定终态、禁止后续调用和迟到改写；保存组件评分遇中断时，后续计划项明确 not_started。另确认同步 native iterator 本身不使用 e2e evaluate 的任务总时限，文档/CLI 已标清适用范围。服务器交接见 [评分恢复](../../native-scoring-recovery.md)。
