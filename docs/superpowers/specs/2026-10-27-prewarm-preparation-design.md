# S4：Agent 阶段预热准备缓存（设计稿，未实现，待用户决定）

日期：2026-10-27。状态：只写设计，不改代码。代码事实基于 `perf/server-speed`（2314d83 之后）。

## 1. 目标与收益

一轮里分析 / 实现 Agent 要工作几十分钟，这段时间服务器的执行资源基本闲着。服务器测速：每题准备 219–351 s，答案 25–292 s，一次执行的墙钟取决于最慢的分区。新鲜确认批次在 claim 之前从没跑过，所以第一次跑必然整批未命中，要从头准备。如果在 Agent 阶段就把下一批新鲜题按父节点的准备代码准备好，新鲜确认那一步就只剩答案阶段，墙钟大约减半。

预热不改变任何比较条件。缓存命中本来就只记在 manifest 里作披露（`prepared_from`），不进 `protocol_id` / `pairing_id`；命中前会逐字节核验，内容和自己准备的一样（`preparation_cache.py` 的 `install`）。

## 2. 预热什么

- **下一批新鲜题**：`claim()` 总是取第一个未用的批次，所以下一批是确定的。用当前父节点 P 冻结的源码去准备。
  - 如果候选只改答案路径（目前的常见情况），父子两边的新鲜运行都会命中。
  - 如果候选改了准备路径，子节点照样未命中、自己准备；父节点那一侧仍然命中。
- **准备路径变了之后重测的分区**：一个改了准备路径的候选被接受后，它成为新的父节点，它的 search / validation 分区在新键下都还没有缓存。下一轮 Agent 阶段可以先按新父节点的源码把这些分区准备好。
- **validation（键没变时）**：C0 已经发布过，本来就会命中，不需要预热。
- **sealed：一律排除**（硬拒绝，复用 `Policy.refuse_sealed`）。理由：
  - sealed 在最终确认前不能被任何运行碰到。
  - 唯一的入口是一次性 claim 加人工确认（`sealed.py`），预热会绕开这个入口。
  - 它只在最后跑一次，预热省下的时间很少。
- **暂不做（二期选项）**：候选冻结后、簇试验期间，用候选自己的准备代码预热它的新鲜批次。这只对改准备路径的候选有用，但簇试验失败时这笔花费就浪费了。

## 3. 泄漏分析（新鲜题、sealed 都不能泄漏）

先说清现状：**Agent 没有技术隔离**。

- 它们以服务器的同一个 OS 用户运行，有完整 shell（`action_requests.py:6`、`context.py:31` 都明确写了不是沙箱）。
- 分析 Agent 的 cwd 是评测仓库；实现 Agent 的 cwd 是 SN worktree。
- 新鲜题、validation、sealed 之所以对 Agent 不可见，靠的是两样东西：`sn-eval` 输出的投影（`splits.Policy.project`），以及简报里的规则（"不要读 `var/`"）。
- artifact store 里的 bundle 早就包含所有分区（含新鲜和 sealed）的问题和文档；SQLite 里的 `protocol_json` 也列出了新鲜批次和 sealed 的 case_id。

所以预热**不会削弱本来就不存在的隔离**，但会新增两处足迹。设计要让这两处足迹不比现状更显眼：

1. **预热运行目录**。现有的分区运行会把本分区的问题文本写进 `product-bundle.json`。处理方式：
   - 预热走"只准备"模式（第 5 节）：不写问题文本，也不写 `planned.jsonl` / `outputs.jsonl`。
   - 运行目录放在 `<output_root>/prewarm/<不透明 id>/`，权限 0700。
   - 不登记为 Job、执行或 attempt，因此任何 `sn-eval` 视图、简报和上下文附件都列不出它。
2. **缓存条目**。`entry.json` 里有 `partition_id` 和 `source_run_dir`，也就是说缓存目录可以看出"哪些分区在 claim 之前就被准备过"，从而推出下一批新鲜题。现状下 C0 之外的分区要到 claim 后才出现在缓存里，所以这是**新增的时间信号**。
   - 这只是对 DB 里已有信息的冗余，可以接受。但要写进简报规则：不读 `preparation-cache/`、`prewarm/`，和现在不读 `var/` 一样。
   - 能否接受，请用户决定（第 7 节第 1 问）。

真正的隔离（Agent 换 OS 用户或进容器，output_root 和 artifact store 对其不可读）是另一件事，不在本设计范围内。如果以后要防"Agent 主动去读"，那样做才算数。

## 4. 记账

- 预热会调用模型（导入、摘要、元数据、嵌入），但不提问。所以**不计入 `max_case_runs`**（那一项是题次），也不计入 `max_runs_per_candidate`。
- 迭代预算账本增加一类条目 `kind='prewarm'`：
  - `case_count=0`，`partition_count=n`，记录归属的父节点和批次（只存服务器端）。
  - 有 `limit_cny` 时，预约按每个分区的准备估价（取历史已结算的准备花费；没有历史时用冷启动值），结算按该运行自己 `budget.json` 的实际花费。
  - 预算策略里新增可选上限 `max_prewarm_partitions`（冻结在协议里）。不设上限就不预热，这样旧迭代的行为不变。
- `_estimate`（按题均价）只用 attempt 的花费。attempt 命中预热缓存后花费会偏低，导致冷启动的 attempt 预约不足。所以均价估算改成"attempt 花费 + 它命中的预热条目花费 ÷ 题次"，或者干脆按"未命中准备"的历史分档估算。实现时二选一。
- 轮次报告和账本汇总里，预热花费单独成行，不摊到某个候选身上，保证"每个被接受的改进花了多少"这笔账是完整的。

## 5. 机制（建议）

- runner 增加"只准备"模式，例如 `execute(..., prepare_only=True)` / `--prepare-only`：
  - 流程：选缓存键 → 拿 KeyLock → 未命中就导入 → 预热诊断通过就发布 → 结束。
  - 已命中就直接结束。
  - 不提问、不评分；保留 `preparation-diagnostics.json`、`preparation-cache.json` 和 S1 的 `speed-diagnostics.json`。
- 工作台增加 `IterationService.prewarm(iteration_id, node_id, scope)`，由轮次编排在进入 Agent 阶段时调用：
  - 内部用 `plan_batch(prepare_only=True)` 起分区进程，用的是父节点冻结的源码捕获，和 attempt 走同一条路径，所以缓存键完全一致。
  - 历史里只记聚合事件：`iteration.prewarm.started/finished`，带分区数、命中 / 新建 / 失败数和花费。不带 batch_id 和 case_id；如果事件对分析 Agent 可见，按投影规则去掉。
- 和真实 attempt 的关系：
  - 预热不占用、也不推进新鲜批次的 claim。
  - 预热用自己较小的并行度。
  - 一旦轮次要派发 attempt，编排就停止启动新的预热分区。正在准备的分区可以完成：发布是原子的，而同键的 attempt 会在 KeyLock 上等它发布后直接命中，不会重复准备。
  - 预热失败（比如基础设施错误）不发布条目，attempt 照常自己准备，结果只是没有加速。
- 模型请求和 attempt 共用 S2 的全局闸门（FIFO，没有优先级）。预热的并行度应留出余量，可以用 S1 的 `speed.gate` 和 `scripts/model_gate_status.py` 观察。

## 6. 方法学注意

- 同一个键只准备一次，之后的所有使用者共用同一份 notebook，所以 k_base 次重复不会采到准备阶段的随机性。这一点现在就成立（C0 准备、候选复用；同键并发运行之间也共用），预热只是让新鲜批次也一样。要在预注册里写明。
- 预热用的是父节点源码。如果父子共用准备路径，他们在新鲜批次上就用同一份 notebook，配对比较更干净；如果准备路径不同，各自用各自的，和现状一样。
