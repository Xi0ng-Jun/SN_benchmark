# 开发计划：与场景无关的部分

状态：2026-11-25 定稿，供下一个对话执行。方法本身见 `method-design.md`。

第 1–6 节是开发安排，属于判断。第 7 节的服务器事实注明了来源；标「未执行过」的命令没有在服务器上跑过。

## 1. 范围

**要做**：设计文档里的「外部程序」。它不含任何场景内容，只通过第 2 节的接口接触场景。

**不做**：选定或接入任何真实场景，包括 ALW。那是之后的事，见第 8 节。

**测试在哪里做**：全部在评测服务器上。本机只写代码。研究员在服务器上执行一条测试命令，把输出贴回来。

## 2. 场景接口

一个场景是一个目录，里面有四样东西：

| 内容 | 说明 |
|---|---|
| 事实配置 | 题目清单、哪些题彼此相关、练习题和考试题的划分、限制、无效运行的判定条件、最终考试的设置、打分原始输出里哪个字段是分数 |
| 运行命令 | 输入：一道题、一个 harness 文件夹、模型出口的地址和这次运行的凭据、输出目录。作用：在这道题的环境里用这个文件夹的启动命令跑一遍，把产出和日志写进输出目录 |
| 打分命令 | 输入：一道题、一份产出、输出目录。作用：执行官方打分，把原始输出写进输出目录 |
| 进入环境命令 | 输入：一道题、要执行的命令。作用：在这道题的环境里执行它，不启动 agent |

外部程序对三条命令的输出不做解读，只保存和转交。唯一用到「分数字段」的地方是最终报告的汇总。

## 3. 测试用的替身

外部程序要在没有任何真实场景的情况下测试，所以测试代码里自带四个替身。它们是测试的一部分，不是场景，不需要研究员决定任何事。

| 替身 | 是什么 | 替代什么 |
|---|---|---|
| 桩场景 | 放在测试目录里的一个最小场景：每道题要求产出一个内容确定的文件，打分脚本逐字段比对。三条命令都是几行脚本 | 真实场景 |
| 做题脚本 | 一个不调用模型的脚本，充当 harness 文件夹的启动命令，按文件夹里的一个设置产出对或错的文件 | 做题 agent |
| 开发脚本 | 一个不调用模型的脚本，在开发沙盒里按固定顺序发起五种操作、改 harness 文件夹 | 开发 agent |
| 桩模型服务 | 测试时启动的一个本地服务，按固定内容回应模型调用，并报告用量 | 模型网关 |

桩场景还要能按测试的要求制造三种情况：运行失败、符合无效条件的运行、打分命令出错。

## 4. 代码安排

- Python，只用标准库，测试用 pytest。需同时能在 3.12 和 3.13 上运行（服务器上的工具是 3.13 的用户级安装）。
- 包名 `harness_builder`，命令 `hb`。测试时用 `PYTHONPATH=src`，不安装到服务器的用户环境里，避免影响 ssap。
- 沙盒的隔离方式是可替换的一层，两种实现：容器（正式使用）和不隔离（只用于不涉及隔离的测试）。
- 沙盒里的小命令和外部程序之间用一个共享目录传递请求和结果，不走网络。

| 模块 | 内容 | 对应规则 |
|---|---|---|
| `scenario` | 读场景目录，调用三条命令 | — |
| `split_lock` | 第一次运行前记下划分的哈希，之后每次启动核对 | 1 |
| `ledger` | 只增不改的记录，每条带上一条的哈希，可以核对是否被改过 | 3 |
| `harness_repo` | harness 文件夹的版本管理；按版本取出只读副本 | 6 |
| `runs` | 运行与打分：取版本、调命令、存全部输出、按事先的条件判定无效 | 2、3 |
| `gateway` | 模型出口：按运行发凭据、计量、限定做题模型、到上限后拒绝 | 4 |
| `sandbox` | 启动开发 agent；挂载材料（只读）、练习题、harness 仓库、工作区、请求目录 | 1 |
| `ops` | 受理沙盒发来的五种操作请求 | — |
| `client` | 放进沙盒的小命令，发起五种操作 | — |
| `materials` | 材料的每次增加存档并记哈希；读提问文件；把回答加为材料 | 5 |
| `delivery` | 冻结、记哈希、全新环境试跑 | 6 |
| `exam` | 按事实配置执行最终考试 | 6 |
| `report` | 从记录生成报告 | — |
| `cli` | 命令行入口 | — |

可以从 ssap 借鉴的代码（`.worktrees/ssap/` 下，复制后修改，不要引用）：

- `src/ssap/targets/alw/harbor_runner.py` 的 `MeteringProxy`：按运行发凭据并计量的做法。需要补上预算上限和模型限定。它只处理过 Claude Code 使用的接口格式。
- `src/ssap/eval/proposer_sandbox.py` 的 `run_proposer_docker` 和 `proposer_command`：在容器里启动一个 agent 会话的做法。
- `src/ssap/eval/event_ledger.py`：记录的写法。

一处要注意：`proposer_command` 启动容器时没有任何限制网络的参数。规则 1 要求沙盒除模型调用外不能访问外部网络，这一点要重新实现并用测试确认，不能照搬。

## 5. 开发顺序

每一步结束时在服务器上跑一次测试。前六步不调用真实模型。

| 步骤 | 做什么 | 完成的标志 |
|---|---|---|
| 1 | `scenario`；桩场景；做题脚本 | 能对桩场景执行三条命令，打分结果与预设一致 |
| 2 | `split_lock`、`ledger`、`harness_repo`、`runs` | 用做题脚本跑完桩场景的全部练习题；记录完整；三种制造出来的情况（失败、无效、打分出错）各自被正确记录 |
| 3 | `gateway`；桩模型服务 | 用量被按运行计入；未指定的模型被拒绝；到上限后的调用被拒绝 |
| 4 | `sandbox`、`ops`、`client`、`materials`；开发脚本 | 开发脚本在容器里走完「改一处、运行、打分、进入环境、提问、收到回答、交付」 |
| 5 | `delivery`、`exam`、`report`、`cli` | 用开发脚本交付的文件夹走完全新环境试跑和最终考试；报告里的每个数字都能在记录里找到 |
| 6 | 六条规则的违反测试 | 六个测试全部被拦住，见下 |
| 7 | 真实 agent 的一次冒烟 | 一个真实的开发 agent 在沙盒里对桩场景成功发起五种操作并交付 |

第 6 步的六个测试：

1. 在开发沙盒里读考试题：应当不存在。在沙盒里访问外部网络：应当失败。
2. 在沙盒里改打分的原始输出：应当没有写权限。
3. 删除或修改一条记录：核对时应当被发现。
4. 做题时调用未指定的模型，或超出预算后继续调用：应当被拒绝。
5. 修改已存档的材料：核对时应当被发现。
6. 交付之后修改 harness 文件夹：哈希不符，考试拒绝执行。

第 7 步用服务器上已有的镜像 `ssap-alw-agent:2.1.302`，里面的 Claude Code 位于 `/opt/claude-code/bin/claude`，模型用 ssap 实验的同一个。这是唯一花模型费的一步，量很小。它只确认通路，不说明方法是否有效。

## 6. 完成之后应当具备的东西

- 一个命令行程序：给它一个场景目录和一个材料文件夹，它能启动开发、受理操作、冻结交付、执行考试、生成报告。
- 一份场景接口的说明，足够让人照着为一个新场景写出场景目录。
- 一套在服务器上一条命令就能跑完的测试。

## 7. 服务器上怎么测

来源：研究员 2026-11-24 在 ssap 主对话里给出的说明，以及该对话里执行成功的命令。

已知的事实：

- 工具（`pytest`、`ssap` 等）装在 `~/.local/bin/`，是 Python 3.13 的用户级安装，没有虚拟环境。用法是 `export PATH="$HOME/.local/bin:$PATH"`。
- ssap 的代码在 `~/autoalw/ssap`，更新方式是本机提交并推送到 `origin`，服务器上 `git pull --ff-only`。
- 研究员通过 SSH 粘贴命令，单次粘贴过长会丢字符。每段命令要控制在 600 字节以内。
- 服务器上有 Docker；可用内存约 259 GiB，没有交换分区；与他人共用，ssap 的并发上限是 4。
- 服务器时钟是 UTC。

实际采用的做法（2026-11-26 第一次在服务器上执行成功，37 个测试通过）：

第一次，单独 clone 新分支，只从 ssap 的检出里读一次仓库地址：

```bash
U=$(git -C ~/autoalw/ssap remote get-url origin)
git clone -b feat/harness-builder --single-branch "$U" ~/autoalw/harness-builder
```

之后每次更新并测试：

```bash
export PATH="$HOME/.local/bin:$PATH"
cd ~/autoalw/harness-builder && git pull --ff-only && python3 --version
PYTHONPATH=src pytest -q tests 2>&1 | tail -30
```

说明：

- 这样做不写 `~/autoalw/ssap` 里的任何文件（包括它的 `.git`），不影响可能正在运行的 ssap Round 2。
- 桩场景的命令用服务器 PATH 里的 `python3`。
- 需要容器的测试会启动容器。测试要自己限定并发和内存，不与 ssap 的运行抢资源。
- 本机的提交和推送需要研究员同意后再做。

## 8. 之后的事（不在下一个对话的范围内）

- 选定并接入真实场景。可以先接一个便宜的，再接 ALW；接 ALW 时把 ssap 已有的启动和打分方式包成三条命令，人写的保底壳可以作为对比对象。
- 接第二个场景时，外部程序的改动行数应为零。不为零的每一处都说明有场景内容漏进了外部程序。
- 方法是否有效，只能由真实场景上的最终考试回答。
