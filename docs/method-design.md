# 方法设计：把一个通用 agent 适配到给定任务

状态：设计草稿，2026-11-25。

- 第 1–11 节是设计，全部属于判断，没有实验支撑。
- 第 12 节是与 `.worktrees/ssap`（分支 `feat/ssap`，提交 `7075999`）现状的对照，属于事实，每条写明依据的文件。
- 第 13 节列出研究员已做的决定和尚未验证的假设。

本文不出现任何具体数值。所有数量都由研究员在使用时给定，汇总在第 5 节。

---

## 1. 要解决的问题

给定三样东西：

- 一组任务；
- 一个通用 agent，即一个现成的 agent 产品加一个固定的模型；
- 研究员手头与这组任务有关的任何材料。

产出一样东西：一个 harness 文件夹。用它启动的做题 agent，在这组任务的官方打分下比通用 agent 得分更高。

付出的代价是 token 和时间。模型不变，变的只是模型外面的东西。

本文里 harness 指模型之外、决定 agent 怎么干活的一切：给模型看的说明、可按需查阅的做法、可调用的工具和脚本、自动触发的检查、时间安排、收尾步骤，以及 agent 产品自身的程序。

harness 文件夹装的是启动做题 agent 所需的、除模型和题目环境之外的全部东西。它的起点是通用 agent 原样的样子，开发 agent 在这个起点上修改。能改到多深取决于通用 agent 是什么产品，见第 8 节。

## 2. 什么时候能用

三个前提，缺一条就不适用：

1. 任务能在隔离的环境里重复运行，运行不会对外部世界造成无法撤销的影响。
2. 有一个可以自动执行的官方打分程序。
3. 任务能分成互不相关的两部分，一部分用来练习，一部分留作最终考试。

方法不承诺一定涨分。它只保证：涨没涨、涨了多少、花了多少，是如实测出来的。

## 3. 设计原则

1. **方法只规定沙盒外面的事。** 沙盒里面怎么干，由 agent 决定。
2. **场景的复杂性留给 agent。** 方法里不出现任何领域概念，也不预设失败有哪几类、改动有哪几类、该分几个阶段。
3. **信息和干活分开。** 外部只提供信息，不替 agent 干活。信息由谁提供、质量如何，方法不关心。
4. **不预设任何数值。** 预算、重复次数、时限、题目数量都由研究员给定。
5. **可信度只来自沙盒外的最终考试。** 沙盒里的任何判断出错，后果只是最终考试考不好，不会让错误的结论被当成正确的。

## 4. 四个角色

| 角色 | 是什么 | 做什么 |
|---|---|---|
| 研究员 | 人 | 提供信息、设定限制、回答问题、做决定 |
| 开发 agent | 一个 agent 产品加一个模型，在沙盒里运行 | 把通用 agent 适配到任务，产出 harness 文件夹 |
| 做题 agent | 某一版 harness 文件夹加做题用的模型 | 做题；它是被改进、被考试的对象 |
| 外部程序 | 方法唯一需要实现的软件，在沙盒外运行 | 执行运行、调用官方打分、记录、计量预算、冻结交付、执行最终考试 |

两点说明：

- 开发 agent 用的模型和做题用的模型可以相同，也可以不同，由研究员定。
- 外部程序不解读分数，不判断好坏，不做任何与领域有关的事。

## 5. 研究员提供什么

| 项目 | 内容 |
|---|---|
| 题目 | 全部任务，以及哪些任务彼此相关（来自同一个底层项目或同一个来源） |
| 划分 | 哪些是练习题，哪些是最终考试题；彼此相关的任务必须在同一侧 |
| 运行方式 | 怎样在一道题的环境里启动一个 agent，怎样取回它的产出 |
| 打分方式 | 怎样对一份产出执行官方打分 |
| 通用 agent | agent 产品及版本；它的哪些部分允许修改；做题用的模型 |
| 开发 agent | agent 产品及版本，开发用的模型 |
| 材料文件夹 | 任何东西，格式不限，可以为空 |
| 开发阶段的限制 | 总预算，单次运行的上限，沙盒里允许做什么 |
| 无效运行的判定条件 | 哪些情况算运行本身无效、需要重跑；可以为空 |
| 最终考试的设置 | 和谁对比，每个对象重复几次，分数怎么汇总，考试题可以使用几次 |

其中「运行方式」和「打分方式」是研究员唯一必须做的准备工作，通常由任务的发布方提供。其余都是信息或决定。

材料文件夹里可以放什么，没有限制：任务的官方文档、工具手册、论文、研究员的笔记、别的模型写的建议、以前做同类任务留下的代码和经验、练习题的参考答案。唯一的禁区见规则 5。

## 6. 六条固定规则

每条规则都由外部程序或沙盒强制，不依赖对 agent 的嘱咐。

### 规则 1：题目隔离

- 划分在任何运行开始之前锁定，之后不改。
- 最终考试题的内容和答案不进沙盒，不进材料文件夹。
- 沙盒不能访问外部网络，模型调用除外。

理由：被考的一方不能接触考卷。

### 规则 2：打分不可改

- 官方打分只由外部程序执行。
- 打分程序输出什么，外部程序就保存什么、返回什么，不做任何再加工。
- 开发 agent 可以自己写程序去读这些输出，那是它的工作产物，不是方法的一部分。

理由：方法自己加的每一层解读都可能出错，而且出错时没有任何报错。

### 规则 3：全部留痕

- 外部程序记录每一次运行、每一次打分、每一笔预算消耗、每一次材料增加、每一次限制变更。
- 记录只增不改。失败的、中断的、无效的运行同样记录。
- 一次运行是否无效，只按研究员事先给的条件判定。条件变更要记录，并对所有版本和所有对比对象同样适用。
- 没有得到官方分数、又不符合无效条件的运行，按任务失败计入，不剔除。

理由：只留下好结果的记录没有意义；把失败悄悄算成无效会抬高分数。

### 规则 4：预算和模型由外部强制

- 所有模型调用都经过外部程序控制的出口，在那里计量。
- 做题 agent 只能调用研究员指定的做题模型。
- 到达预算上限后，外部程序不再受理新的运行。

理由：否则「多花预算」或「换了更强的模型」会被当成「harness 更好」。

### 规则 5：材料只增不改，提供者受限

- 材料文件夹里的每一次增加、每一个问题和回答，都原样存档。
- 往材料文件夹里加东西的人或模型，不得接触过最终考试题的内容、答案或考试结果。

理由：材料是外部贡献的全部，必须可以事后查看；而材料是考试信息泄漏的唯一入口。

### 规则 6：交付冻结，考试只按规定次数进行

- 交付时外部程序冻结 harness 文件夹并记下它的哈希，之后不能改。
- 考试之前，外部程序在一个全新的环境里用交付的文件夹跑一道练习题。跑不通就退回，不算考试。
- 最终考试题只使用研究员事先规定的次数。
- 考试时，做题 agent 和每个对比对象使用同样的运行方式、打分方式、限制和无效条件。
- 考试结果不得回流到同一次开发中。

理由：开发时好用的东西可能悄悄依赖沙盒里才有的文件或路径；考试题一旦被反复使用就不再是考试。

## 7. 开发 agent 手里有什么

### 7.1 能看到的

- 材料文件夹；
- 全部练习题，以及练习题的参考答案（如果有）；
- 全部运行记录，包括每次运行的完整工作目录和日志原文，不是摘要；
- 剩余预算。

### 7.2 能做的

这些操作都由外部程序提供。

| 操作 | 作用 | 是否调用模型 |
|---|---|---|
| 运行 | 指定一个 harness 版本和一道练习题，让做题 agent 跑一遍；返回官方打分的原始输出、完整工作目录和日志 | 是 |
| 打分 | 对任意一份产出执行官方打分；这份产出可以来自以前的运行，也可以是它自己构造的 | 否 |
| 进入题目环境 | 打开一道练习题的环境，直接使用里面的工具，不启动做题 agent | 否 |
| 提问 | 往提问文件里写问题 | 否 |
| 交付 | 指定一个 harness 版本作为交付 | 否 |

后两种不调用模型的操作（打分、进入题目环境）是给贵任务准备的：整次运行很贵时，开发 agent 仍然有便宜的办法了解打分规则和工具行为。

### 7.3 能改的

- harness 文件夹里的任何东西；
- 它自己的工作区：笔记、脚本、任何辅助文件。

### 7.4 中断和重启

开发 agent 可能因为上下文用尽、故障或预算分期而多次重启。方法要求它的全部记忆都在工作区文件和运行记录里。外部程序不替它保存对话。

## 8. harness 文件夹

这是方法的交付物。硬性要求只有两条：

1. **一条启动命令。** 外部程序把文件夹以只读方式放进题目环境，然后执行这条命令。从这一刻到运行结束，发生什么都由文件夹里的东西决定。
2. **一份清单。** 用直白的文字列出文件夹里有哪些部分。每个部分写明：它做什么；为什么加它（依据哪份材料、哪个回答，或哪次运行里看到的什么现象）；去掉它会怎样。

其余结构不规定。文件夹用版本管理，每次运行记录它用的是哪个版本。

### 8.1 可以改到多深

改 harness 有两种深度，文件夹这种形式对两种都适用：

- **通过产品提供的方式改。** 多数 agent 产品允许在不动它自身程序的前提下加东西：说明文件、做法文件、自定义工具、在特定时机自动执行的脚本、配置项；也可以在它外面包一层程序来管时间和收尾。文件夹里放的是这些附加内容，启动命令调用原样的产品。
- **改产品自身的程序。** 如果产品的源码是公开的，文件夹里可以直接放一份修改过的产品，启动命令调用这一份。这样能改到前一种方式够不着的地方，例如它怎样管理上下文、怎样截断工具输出、怎样组织多步操作。

哪一种可行，由通用 agent 是什么产品决定，不由方法决定：源码不公开的产品只能用第一种。研究员在第 5 节「哪些部分允许修改」里写明。方法对两种一视同仁：都是文件夹的一个版本，都用同样的方式运行、打分和记录。

### 8.2 一种建议的摆法

下面的摆法不是规定，用不到的部分留空：

| 部分 | 内容 |
|---|---|
| 说明 | 做题 agent 开工时必读的一页：任务是什么，怎么算分，常见的坑 |
| 做法 | 若干短文件，遇到具体情况时按需查阅 |
| 工具 | 做题 agent 可以主动调用的命令和脚本 |
| 自动检查 | 在特定时机自动执行的检查，例如修改文件之后、交卷之前 |
| 运行设置 | 时间怎么分配，是否保留中间结果的备份，收尾时做什么 |

## 9. 流程

方法只规定三个时刻：开始、进行中、交付。

### 9.1 开始

1. 研究员准备好第 5 节的全部内容。
2. 外部程序确认划分已经锁定，启动沙盒。
3. 外部程序把一份初始说明交给开发 agent。

初始说明是一段固定的文字，不含任何领域内容，包括五部分：

- 目标：第 1 节。
- 手里有什么：第 7 节。
- 交付要求：第 8 节。
- 怎么提问：见 9.2。
- 默认的工作习惯：见下。

默认的工作习惯是建议，不强制，开发 agent 可以不照做：

1. 先读材料，写下自己对任务和打分方式的理解。
2. 改任何东西之前，先让通用 agent 原样跑一次，确认运行和打分能正常工作。
3. 用结果确定的产出核对打分：空的产出、故意弄坏的产出、同一份产出打两次。
4. 先用便宜的办法试（打分、进入题目环境），再花整次运行。
5. 每次运行之后读日志原文，不只看分数。
6. 每次整跑之前写下预期，跑完对照。
7. 记住每个测过的版本的分数，交付测过的版本里最好的那个。
8. 定期把进展和待办写进工作区，以便重启后接上。

### 9.2 进行中

开发 agent 自己决定读什么、跑哪道题、改什么、什么时候停。方法不规定。

研究员可以随时做五件事：读记录、回答问题、往材料文件夹里加东西、调整限制、叫停。调整限制会被记录。

提问的方式：

- 开发 agent 遇到材料里找不到、自己又无法通过运行查清的事，或者需要有权的人拍板的事，就写进提问文件。
- 每个问题写三样：问什么；为什么自己查不到或定不了；没有回答时按什么假设继续。
- 提问不阻塞。没有回答时，开发 agent 按它写下的假设继续。
- 回答作为新材料加进材料文件夹，受规则 5 约束。

### 9.3 交付和考试

1. 开发 agent 指定一个版本作为交付。预算用完时，以它最后一次指定的版本为准；如果从未指定，记为没有交付。
2. 外部程序冻结这个版本。
3. 外部程序在全新的环境里用它跑一道练习题。跑不通则退回；如果还有预算，开发 agent 可以修复后重新交付。
4. 外部程序按研究员的设置执行最终考试。
5. 外部程序生成报告。

## 10. 报告

报告只包含原始事实：

- **分数**：每个对比对象在每道考试题、每次重复上的官方原始分数，以及按研究员规定的方式汇总的结果。
- **花费**：开发阶段的总花费；考试时每个对比对象每次运行的花费。
- **开发过程**：运行次数、打分次数、问题数和回答数、材料增加的次数、限制变更、无效运行及其原因。
- **交付物**：harness 文件夹的哈希和它的清单。

是否采用交付的 harness，由研究员看这些数字决定。方法不用统计显著性检验来自动否决，这延续 ssap 的约定（`.worktrees/ssap/AGENTS.md` 不变式 3）。

对比对象由研究员定。两个有用的选择：

- 通用 agent 原样做题。
- 通用 agent 做题时直接拿到同一个材料文件夹。这一行回答的是：涨分有多少只是因为材料本身。

## 11. 方法不规定的事，以及已知的失败方式

### 11.1 不规定的事

下面这些都是开发 agent 的选择。以前的经验可以作为材料提供，但不是规则：

- 写不写检查、写哪些检查、检查有多大权力；
- 是否保留中间结果的备份，备份在什么条件下更新；
- 怎么诊断失分，失分分成几类；
- 一次改一处还是几处；
- 是否自己留几道练习题不看，用来检查有没有背题；
- 是否建立带标签的样本集来离线检验自己写的检查；
- 时间怎么分配，是否预留收尾时间。

### 11.2 已知的失败方式

| 失败方式 | 由什么兜住 | 兜不住的部分 |
|---|---|---|
| 背练习题，换题就失效 | 规则 1；最终考试 | 只有考试时才知道，此时预算已花完 |
| 开发 agent 自己读分的程序写错 | 规则 2 保证原始输出始终可得 | 它可能一直按错的读数优化，考试才暴露 |
| 研究员给的运行方式或打分方式本身有错 | 默认工作习惯第 2、3 条；提问 | 开发 agent 没有照做时无人发现 |
| 把失败算成无效运行 | 规则 3 | 研究员给的无效条件本身定得不对 |
| 改坏了以前好的版本 | 版本管理加运行记录；默认工作习惯第 7 条 | 开发 agent 没有照做 |
| 预算花完没有进展 | 规则 4 限制损失 | 花掉的预算 |
| 考试信息经材料或回答泄漏 | 规则 5 | 靠人遵守，无法由程序检查 |
| 交付物只在开发沙盒里能用 | 规则 6 的全新环境试跑 | 只试一道题，覆盖有限 |
| 开发 agent 能力不够 | 无 | 表现为没有涨分，与「方法无效」无法区分 |
| 整次运行很贵、练习题很少，分数变化分不清是改进还是波动 | 打分和进入题目环境这两种便宜的操作 | 小幅改进在这种条件下测不出来 |

最后两条是这个设计最大的不确定点，见第 13 节。

## 12. ssap 在 ALW 上的实验与本方法的对照

结论：结构上它是本方法的一个特例，前提是把「开发 agent」理解为前后两段由不同的执行者担任；另有四处不符合本方法的规则。

以下各条依据的文件都在 `.worktrees/ssap` 下。

### 12.1 对应关系

| 本方法 | ssap 在 ALW 上的对应 | 依据 |
|---|---|---|
| 研究员 | 用户本人 | — |
| 开发 agent，适配阶段 | 研究员与外部 agent 合作完成：写保底壳和领域检查，逐级上机调试 | `docs/alw-deployment-log.md`；`container/alw/`；`src/ssap/checkers/alw/` |
| 开发 agent，改进阶段 | 沙盒里的提案 agent，每轮提一处改动 | `src/ssap/eval/proposer_sandbox.py`；`src/ssap/eval/auto_loop.py` |
| 做题 agent | Claude Code 固定版本加网关上的固定模型 | `configs/alw/config.server.json` 的 `agent` 段 |
| 外部程序 | `ssap` 命令行及其运行、收集、记录模块 | `src/ssap/cli.py`；`src/ssap/targets/alw/harbor_runner.py`；`src/ssap/targets/alw/harvest.py` |
| 题目与划分 | 按电路簇划分为练习、验证、测试三部分 | `configs/alw/split.json`；`configs/alw/clusters.json` |
| 运行方式 | 通过 Harbor 启动容器 | `src/ssap/targets/alw/harbor_runner.py` |
| 打分方式 | 基准自带的验收镜像，未改动 | `configs/alw/config.server.json` 的 `images.verifier_image` |
| harness 文件夹 | `container/alw/` 加通用部分和领域检查，容器内位于 `/opt/harness` | `container/alw/`；`src/ssap/kernel/`；`src/ssap/checkers/alw/` |
| 记录 | 事件账本和故障账本 | `src/ssap/eval/event_ledger.py`；`src/ssap/eval/infra_ledger.py` |
| 预算和模型的外部强制 | 计量代理；模型槽位统一锁定；单题资源上限 | `configs/alw/config.server.json` 的 `gateway`、`model_homogeneity`、`run` 段 |
| 无效运行的判定条件 | 网关等待占比上限等故障条件 | `configs/alw/config.server.json` 的 `gateway.theta_gw_max`；`src/ssap/eval/infra_ledger.py` |
| 最终考试 | 验证集上比一次，测试集只开封一次、多个种子 | `src/ssap/cli.py` 的 `c1-val` 和 `alw-report`；`AGENTS.md` 不变式 3 |
| 对比对象 | 原始 → 人写保底壳 → 自动改进版；另有两个对照 | `AGENTS.md` 不变式 3；`docs/mcr-plain.md` 第 6 节 |

### 12.2 ssap 多规定的东西

下面这些在 ssap 里是规则，在本方法里属于开发一方自己的选择（第 11.1 节）：

- 改动分四类，各有权限和离线筛查方式（`docs/mcr-plain.md` 第 3 节）。
- 交卷区只进不退、禁止中途强制回滚、只有与考官一致的检查才能覆盖（`AGENTS.md` 不变式 1）。
- 练习题内部再遮住一部分不给提案 agent 看（`src/ssap/bank/blind_clusters.py`）。
- 禁止在 harness 里写针对任务的做法和提示词教程（`src/ssap/eval/proposer_sandbox.py` 的提案规则）。
- 提案 agent 只能改指定路径（同文件的 `ALLOWED_PREFIXES`）。
- 练习题的参考答案不给 agent 看，只存在于隔离的检验环境中（`AGENTS.md` 的防泄漏约定）。

另外，ssap 对 harness 的修改全部属于第 8.1 节的第一种：`container/alw/Dockerfile.agent` 安装原样的 Claude Code，`container/alw/bin/mcr_entrypoint.py` 在它外面包一层，`container/alw/bin/mcr_hook.py` 和 `container/alw/settings.json` 用的是产品提供的扩展方式。

### 12.3 ssap 不符合本方法的四处

1. **规则 2**：ssap 自己写了一层读分程序（`src/ssap/targets/alw/metrics_reader.py`），属于方法一侧而不是 agent 的产物。这一层出过错（`docs/alw-deployment-log.md` 第 6.2 节）。
2. **规则 5**：材料没有作为一个只增不改的文件夹存档；研究员与外部 agent 的问答散落在对话记录里。
3. **规则 6**：没有看到「考试前在全新环境里试跑」这一步。这一条我没有逐一核对全部命令。
4. **适配阶段不在沙盒里**：研究员与外部 agent 的工作没有预算计量，也没有受外部程序的任何约束。

第 4 处正是本方法要改变的地方：把适配阶段也交给沙盒里的开发 agent。

## 13. 待定事项

### 13.1 研究员已做的决定（2026-11-25）

1. **ssap 的不变式 1 降为材料。** 「只进不退、禁止中途回滚、只有与考官一致的检查才能覆盖」在本方法里不是规则，而是可供开发 agent 参考的经验。这与 `.worktrees/ssap/AGENTS.md` 的现行约定不同；ssap 工作树内的实验仍按它自己的约定进行。
2. **允许开发 agent 看到练习题的参考答案。** 本方法只禁止最终考试题的内容和答案。

### 13.2 尚未验证的假设

1. 开发 agent 有能力独立完成适配工作。ssap 里这部分是研究员与外部 agent 合作完成的。
2. 开发 agent 会主动核对运行和打分是否正常，而不是只盯着分数改。如果它不会，默认工作习惯的第 2、3 条就要升为固定步骤。
3. 整次运行很贵、练习题很少时，开发 agent 靠便宜的操作和日志原文仍能做出有效的改动。

### 13.3 建议的第一个验证

用 ssap 已有的数据，不需要任何新的整次运行：

- 把第一批实测修复之前的原始运行目录交给一个候选的开发 agent，只包含提案 agent 当时可见的题目。
- 只问一个问题：这里有什么问题。
- 答案是已知的，记录在 `.worktrees/ssap/docs/alw-deployment-log.md` 第 4.3 节和第 6.2 节。
- 数它指出了其中几条。

这直接检验假设 2，也部分检验假设 1。结果决定「核对运行和打分」是留作建议还是升为固定步骤，以及开发 agent 需要用多强的模型。

答案清单（2026-11-25 在看到任何结果之前写定，依据 `.worktrees/ssap/docs/alw-deployment-log.md` 第 4.3 节）。只用第一批实测中提案 agent 可见的 2 道题：

| 编号 | 已知问题 | 线索所在 |
|---|---|---|
| K1 | 宿主机把每次运行都标成网关故障，但失败请求数和重试数都是 0；按当时的规则这些有效运行会被丢弃 | `launch_results.json` 的代理统计 |
| K2 | 从预警到强制停止的时间太短；其中一次运行到停止时还没有交出任何产出，得 0 分 | 运行快照里的时间设置、主阶段的结束方式、交接记录 |
| K3 | 收尾修复因为轮数上限而结束，只用了几分钟，大部分时间预算没有用上，也没有带来改进 | 修复阶段的日志和修复记录 |
| K4 | 收尾修复沿用了主阶段的一个临时配置路径 | 运行快照里记录的主阶段启动参数 |

读分程序把损坏文件标成有效这一条（第 6.2 节）的线索不在这两次运行里，不计入。

做法：把这两次运行的原始目录和对应的宿主机记录交给候选的开发 agent，题目只有一句「这里有什么问题」，不提示该看哪一类问题。如果它漏掉 K1，再跑第二次，题目里加一句默认工作习惯（「先确认运行和记录本身是否正常」），看这一句是否足够。两次的差别直接对应「留作建议还是升为固定步骤」这个决定。

数据在哪里（2026-11-25 核对）：

- 原始运行目录和做题 agent 的完整日志只在服务器上，本机没有。
- 本机 `.worktrees/ssap/docs/server-info/` 里只有从服务器抽取的摘要：`forensic.json`、`out.json`（第一批 3 题实测，其中 1 题属于 ssap 里被遮住的那部分）和 `phase2_bank_report.json`（读分程序修复之前的检验报告）。
- 用这些摘要可以在本机做一个缩小版。它比完整版容易：摘要是人挑过的，「该去哪里找」这一步已经被替它做了。所以缩小版里没指出问题是有力的反面证据，指出了问题只是较弱的正面证据。
