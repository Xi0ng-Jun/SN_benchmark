## 流程

**Smoke（先跑，上限 ¥2）**：创建 smoke iteration（payload `var/lcd-r1/lcd-smoke-create.json`），C0 `attempts = 2`，人工确认。检查：(1) 两题 100 篇全部 `extracted`、100 条非空 summary、chunk 全有 embedding；(2) 第 2 次 attempt 命中准备缓存，导入 0 篇；(3) 答案合成是否出现 10 月初的"SN 拒绝不完整 JSON"失败，若两题都失败则停下查 SN，不进入 R1；(4) 记录每题准备墙钟、每题成本、429 次数。数字不作判读。

**R1-mini（smoke 通过后，上限 ¥20）**，一轮：
1. 创建 iteration（payload `var/lcd-r1/lcd-r1-create.json`）；C0 `attempts = 2`，人工确认。
2. 分析 Agent `cluster propose` ≤ 6 簇；记账人重扫冻结（成员、q、m、v）。
3. 按 |C|·(1−q)·max(m, v, 0.3) 取前 2 簇；每簇一张带 `contract` 的假设卡（cluster_id、predicted_flips ⊆ 成员、guards），人工批准；派生候选；创建实现者（看脱敏簇证据，不含 gold）。
4. 实现者改 SN → freeze → cluster-run（预算内自动）→ 可再改一次 → run `attempts = 2`（预算内自动）。
5. 门判定写入候选 decision。accept 的候选由分析者请求 fresh-run（预算内自动）。
6. 两个候选都 accept 时按 `integrated_from` 合并派生并重跑 validation；低于基准减 η 则撤回。
7. `iteration ledger`，写运行记录。

## 口径

- η 与逐题带来自同一候选 2 次 attempt 的差（Jeffreys 平滑 90% 半宽）；ASQA 每分区一题，族 = 分区，n_eff = n。
- ρ = predicted_flips 中父侧 < 0.5 ≤ 候选侧且 Δ 超带的比例。
- 门：Δ_validation ≥ −η 且 ρ ≥ τ 且 guard 未破 → accept；Δ > η 且 ρ < τ → audit；基础设施失败率上升超带 → unmeasurable；否则 reject。
- 基础设施失败：status ∈ {error, missing}（含 429、导入失败、超时、答案合成失败），单列，不入干净分母，不删除。带题级 error 的执行为 finished、可准入（P2 的行为）。
- 三笔账：采样账 k = 1、S(B) = 种子；过拟合账 K、n_eff、期望偏差 η·√(2 ln K)、validation Δ 对 fresh Δ 的配对差；结构账每笔合同的 ρ 与 verdict、audit 数、愿望清单。

## 判读规则（预先固定）

1. 主结果：validation 均分 Δ > 0 但门未 accept 的候选数 N₁，其中做了 fresh 且 fresh Δ ≤ 0 的数目 N₂。
2. accept 候选在 fresh 上成立（Δ ≥ −η）的比例。
3. 簇复现：冻结簇与已知 ASQA 失败形态（10 月初的答案合成拒绝、检索未召回、冗长答案低 str_em）的对应，人工对照记录。
4. 基础设施失败率 > 25% 则本轮不可判读。不以均分、不以单题翻转下结论。

**发现**：
1. 准备策略是默认的 `per-source-metadata-v1`，不是 `deferred-notebook-metadata-v1`（后者需在 job 配置里显式设 `preparation_policy`，本预注册与 payload 均未设）。于是每题 `notebook_metadata` 调用 400 次，占导入 chat 调用（600 次）的 2/3；其余每篇各 1 次 source_summary、paper_metadata、元素 embedding、chunk embedding。
