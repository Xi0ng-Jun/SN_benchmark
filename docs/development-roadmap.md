# 评测项目下一步开发讨论稿

日期：2026-09-10。本文是建议顺序，尚未授权实施新的功能或恢复在线评分。

## 出发点

目标仍是建立 Silicon Notebook 的持续评测闭环。设计依据是产品真实能力与 DeepEval 可用输入、指标和运行方式。已有实验仅证明部分接入可行；“运行过”“产物完整”“产品答得好”“judge 可靠”必须分别说明。

当前最需要补齐的是：用户能读懂评测对象和结果，开发者能据此定位问题。单纯扩大题数、加 metrics 或追求自动运行频率无法替代这一步。

## 建议顺序与交付物

| 顺序 | 工作 | 具体交付 | 如何验收 |
|---|---|---|---|
| 1 | 产品能力与 DeepEval 对应表 | 产品入口、场景、预期行为、真实可采集字段、metric、限制 | 每个主指标都能指向一个产品问题与可靠输入；缺失观测明确列出 |
| 2 | 一题到底的评测说明与协议 | 用真实保存样本展示文档、问题、Ask 请求、实际上下文、答案、test case、score、汇总；附字段解释 | 非工程背景读者能沿同一 ID 追到分数依据；教学例子与实际观测有明显标识 |
| 3 | 可查看状态的统一入口 | 显示计划数、完成数、失败/跳过/缺失、最后活动时间、进程状态、报告是否过期；先用 CLI 或静态页面 | 进程消失但无结束记录时明确为中断/未知；报告可从保存结果刷新，无需模型调用 |
| 4 | 人工评审与问题分类 | 复用已准备的 40 份材料；明确正确性、忠实性、引用支持与无法判断的标注规则；加入澄清/拒答解释 | 人工标签由人填写；能区分产品行为、数据不适配、judge 分歧和采集缺陷 |
| 5 | 产品场景集与版本比较 | 根据前四步选择小规模真实产品场景；固定数据、证据、预期行为与比较口径 | 同一问题可解释改进或回退；评分协议改变时不直接比较旧分数 |

产品场景优先考虑事实定位、文档间比较、数字/日期计算、引用追溯和需要澄清的问题。公开阅读理解中的指代可能依赖题目原段落，把问题放入 200 段检索库后需要单独讨论适配性，不能直接将所有澄清视为产品 bug。

## 几条路线的取舍

- 推荐先做产品能力表与完整样例，再补状态入口和人工评审：优先解决“评什么、如何读懂、为何失败”。
- 先扩大公开 benchmark：覆盖更多通用题型，但会增加成本，现有解释和校准缺口仍在。
- 先建设完整 Web 平台：浏览体验更好，但会增加界面、存储和权限维护；目前可先采用静态报告或轻量 CLI。

## 后续进入条件

- 恢复在线 baseline 前：用户重新提出运行，核对保存输入、产品版本、judge 身份和未完成记录；不静默重评失败。
- 扩展中文/半导体场景前：明确文档来源、许可/脱敏、版本与人工证据标注；模型生成的问题只作为候选。
- 增加 KG、重排、PDF/OCR 等专项前：先在产品能力表中标出待回答的具体问题，再决定数据与指标。
- 重新启用定时任务前：完善进程状态与报告新鲜度，明确运行成本及完整 baseline；质量门槛仍需人审校准后另定。

本次仓库发布仅整理已有项目和状态文档，未开始上述新功能。下一轮建议先完成第 1、2 项，再据用户阅读与核验反馈决定状态入口的形式。
