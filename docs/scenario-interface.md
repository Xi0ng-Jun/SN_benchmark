# 场景接口

外部程序只通过这里规定的东西接触一个场景。照着这份说明写出一个场景目录，就能把一个新任务接进来。

状态：第 1–5 步写定了题目、划分、三条命令、分数位置、初始 harness、时限、无效运行的判定命令、预算、模型出口、开发 agent、研究员固定的做题设置、最终考试的设置，以及交付检查、考试、报告和主机一侧的命令（第 5–8 节）。

例子：`tests/stub_scenario/` 是测试用的桩场景，下文的每一项它都有。

## 1. 场景目录里有什么

```
<场景目录>/
  scenario.json      事实配置
  <三条命令>          路径和形式由 scenario.json 指定
  <初始 harness>      通用 agent 原样的样子
  <对比用的 harness>  可选，考试时与交付的 harness 对比（见 2.11）
  <各题的可见文件>     可选
```

除 `scenario.json` 之外，目录里怎么摆由场景作者决定。场景目录本身不进开发沙盒；进沙盒的只有练习题的可见文件（见 2.1）。考试题的内容和答案可以放在场景目录里。

## 2. scenario.json

一个 JSON 对象，只能有下面这些键。除 `solver_settings` 可以不写之外，缺一不可。

```json
{
  "tasks": [
    {"id": "p1", "files": "tasks/p1"},
    {"id": "p2", "group": "g1", "files": "tasks/p2"},
    "e1"
  ],
  "split": {"practice": ["p1", "p2"], "exam": ["e1"]},
  "commands": {
    "run":   ["python3", "run.py"],
    "score": ["python3", "score.py"],
    "enter": ["python3", "enter.py"],
    "invalid": ["python3", "invalid.py"]
  },
  "score": {"file": "score.json", "key": "score"},
  "initial_harness": "harness",
  "limits": {
    "run_seconds": 3600, "score_seconds": 600, "enter_seconds": 300,
    "run_budget": {"total_tokens": 20000000},
    "dev_budget": {"total_tokens": 500000000},
    "dev_seconds": 86400,
    "parallel_runs": 4
  },
  "models": {
    "solver": "<做题模型>",
    "developer": "<开发模型>",
    "upstream_url": "${UPSTREAM_URL}",
    "upstream_key_env": "UPSTREAM_KEY"
  },
  "developer": {
    "command": ["sh", "-c", "<在沙盒里启动开发 agent 的命令>"],
    "image": "<镜像>",
    "memory": "16g",
    "cpus": 4
  },
  "solver_settings": {"thinking": "high", "max_output_tokens": "32000"},
  "exam": {
    "compare": {"general": "harness"},
    "repeats": 3,
    "aggregate": "mean",
    "failure_score": 0,
    "invalid_reruns": 1,
    "uses": 1
  }
}
```

例子里的数都只是写法示意。方法不预设任何数值，每一个都由研究员给定。

### 2.1 tasks

全部题目。每项是一个对象，或者只写题目编号的字符串。

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | 是 | 题目编号。只能用字母、数字、`.`、`_`、`-`，首字符是字母或数字 |
| `group` | 否 | 相关题目的组名。来自同一个底层项目或同一个来源的题目写同一个组名。不写时每题自成一组 |
| `files` | 否 | 一个目录，相对场景目录。这道题是练习题时，开发 agent 能读到它（题面、参考答案等）。考试题的这一项永远不进沙盒 |

### 2.2 split

`practice` 是练习题，`exam` 是最终考试题。

- 每道题恰好在一侧，两侧都不能为空。
- 同一组的题必须在同一侧。
- 练习题的 `files` 不能包含场景目录本身，也不能与任何考试题的 `files` 互相包含。

### 2.3 commands

`run`、`score`、`enter` 三条命令必填，`invalid`（无效运行的判定命令，见 3.5）可选。各是一个参数列表。外部程序在场景目录里执行它们（当前目录就是场景目录），所以相对路径按场景目录解析。

### 2.4 score

打分原始输出里哪个位置是分数。只有最终考试的记分和汇总用到它（第 6 节）；外部程序在其他任何地方都不读分数。

| 字段 | 含义 |
|---|---|
| `file` | 打分输出目录里的一个文件，相对路径 |
| `key` | 可选。有时，文件按 JSON 读，用点号分隔的键逐层取值；没有时，整个文件的内容就是一个数 |

取不到、不是数、或不是有限数时，记为没有得到分数。

### 2.5 initial_harness

初始 harness 文件夹，相对场景目录，即通用 agent 原样的样子。外部程序第一次打开状态目录时把它存为版本 `v0`。开发从它开始，它也是一个自然的对比对象。要求见第 4 节。

### 2.6 limits

七个键都必须写。

| 键 | 限制什么 | 值 |
|---|---|---|
| `run_seconds` | 一次运行命令。开发 agent 可以为某一次运行要求更短的时限（见 2.9），不能更长；交付试跑和考试的运行总是用这个值 | 秒，正数或 `null`（不限） |
| `score_seconds` | 一次打分命令，以及一次无效运行判定命令 | 同上 |
| `enter_seconds` | 一次进入环境命令 | 同上 |
| `run_budget` | 一次运行里做题 agent 的模型用量 | 上限表，或 `null`（不限） |
| `dev_budget` | 整个开发阶段的模型用量：开发 agent 自己的调用加上它发起的运行 | 同上 |
| `dev_seconds` | 整个开发阶段的时长，各次开发会话累计 | 秒，正数或 `null` |
| `parallel_runs` | 开发阶段同时进行的运行和打分的个数；考试时同时进行的运行个数 | 正整数 |

上限表把下列计数中的若干个映射到正整数：`requests`（转发出去的请求数）、`input_tokens`（未命中缓存的输入）、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`total_tokens`（前四种之和）。任何一个计数达到上限后，之后的模型调用被拒绝；`dev_budget` 到顶后，新的运行也不再受理。已经在途的请求不打断，所以实际用量可能略超上限，超出的部分不超过到顶那一刻在途的请求。

### 2.8 models

| 键 | 必填 | 含义 |
|---|---|---|
| `solver` | 是 | 做题模型。做题 agent 只能调用它 |
| `developer` | 是 | 开发模型。开发 agent 只能调用它 |
| `upstream_url` | 是 | 上游模型服务的地址，可以写 `${变量}` 或 `${变量:-默认值}`，从环境变量取 |
| `upstream_key_env` | 是 | 存放上游密钥的环境变量名。密钥不写进任何文件，也不会传给场景的命令 |
| `upstream_auth_header` | 否 | 上游要求的认证头，默认 `x-api-key`；OpenAI 式服务写 `authorization` |
| `upstream_auth_prefix` | 否 | 认证头的前缀，默认空；OpenAI 式服务写 `Bearer ` |
| `listen_host`、`listen_port` | 否 | 模型出口监听的地址和端口，默认 `127.0.0.1` 和任意空闲端口 |
| `url_host` | 否 | 交给运行命令的地址里用的主机名，默认与 `listen_host` 相同。题目环境是容器时，写容器里能访问宿主机的名字，并把 `listen_host` 设成容器能连到的地址 |

模型出口的行为：

- 每次运行单独发一个凭据，只能用于 `solver` 模型，运行结束即作废。
- 请求必须是 JSON，`model` 字段必须等于凭据绑定的模型，否则拒绝（不转发）。GET 请求不检查模型。
- 转发时去掉客户端的认证头，换上上游密钥。不重试，不缓存。
- 从响应里读用量，认 Anthropic Messages 和 OpenAI chat 两种格式，流式和非流式都可以。
- 一个请求的用量在客户端看到响应结束之前记账，所以逐个发请求的客户端在到顶后一定会被拒绝；超出上限的只可能是同时在途的请求。
- 每个请求在状态目录的请求日志里记一行。预算的累计从这份日志算，外部程序重启后不清零。

### 2.7 改动配置

- 划分（每道题在哪一侧、属于哪一组）在第一次打开状态目录时锁定，之后改动会被拒绝。
- 其他内容可以改。每次打开状态目录时，外部程序计算场景目录的哈希；它或 `scenario.json` 有任何变化，就把新的哈希和配置原文写进记录。限制和无效条件的每次变更因此都留在记录里。
- 状态目录不能放在场景目录里面。

### 2.9 developer

开发 agent 在沙盒里怎么启动。

| 键 | 必填 | 含义 |
|---|---|---|
| `command` | 是 | 在沙盒里启动开发 agent 的命令，参数列表。命令退出即本次开发会话结束 |
| `image` | 容器沙盒必填 | 沙盒用的 Docker 镜像。镜像里要有 `python3`（`hb` 命令和模型转发用） |
| `python` | 否 | 镜像里 python3 的路径，默认按 PATH 找 |
| `memory`、`cpus`、`pids_limit` | 否 | 容器的内存、CPU、进程数上限 |

沙盒里能看到什么（变量是沙盒里的环境变量；容器沙盒里路径固定如括号内）：

| 变量 | 内容 | 权限 |
|---|---|---|
| `HB_BRIEF`（`/hb/BRIEF.md`） | 固定的初始说明，不含领域内容 | 只读 |
| `HB_MATERIALS`（`/materials`） | 材料，每次增加一个编号子目录；回答也在这里 | 只读 |
| `HB_TASKS`（`/tasks`） | 每道练习题一个子目录，内容是它的 `files` | 只读 |
| `HB_RECORDS`（`/records`） | 开发阶段的全部运行、打分、进入环境的记录 | 只读 |
| `HB_VERSIONS`（`/versions`） | harness 的全部版本 | 只读 |
| `HB_WORKSPACE`（`/workspace`） | 工作区；`harness/` 是 harness 的可改副本，第一次从 `v0` 复制 | 可写 |
| `HB_MODEL_URL`、`HB_MODEL_KEY`、`HB_MODEL` | 模型出口、本次会话的凭据、开发模型 | — |

`hb` 命令在 PATH 上，提供运行、打分、进入环境、提问、交付五种操作和 `status`（用量、剩余预算和时间、版本、问题、交付、每次交付检查的结果、单次运行的时限、研究员固定的做题设置）。容器沙盒没有任何网络（`--network none`），模型调用经挂进来的套接字转到模型出口。考试题、考试记录、总记录、场景目录都不在沙盒里。

一次运行可以要求更短的时限：`hb run 题目 --seconds N`。开发 agent 常常只需要看一次运行的前一段，不必等它跑满。规则：

- `N` 必须是正数；`limits.run_seconds` 不是 `null` 时，`N` 不能超过它。不合要求的请求被拒绝，不产生运行。
- 不写 `--seconds` 时用 `limits.run_seconds`。
- 实际使用的时限写进这次运行的记录（`record.json` 和总记录里的 `run_seconds`）。到时限被结束的运行照常打分、照常记录。
- 只有开发阶段的运行可以这样要求。交付试跑和考试的运行总是用 `limits.run_seconds`。

### 2.10 solver_settings（可选）

研究员为做题 agent 固定的设置，例如思考强度、单次输出上限。一个扁平的对象，名字和值都是字符串；名字只能用字母、数字和下划线，首字符不是数字。不写等于空。

- 外部程序在每一次运行（开发阶段的运行、交付试跑、考试）都把它们原样交给运行命令，每项一个环境变量 `HB_SETTING_<名字>`（见 3.2）。打分、进入环境和无效判定命令收不到。
- 值只来自 `scenario.json`。harness 文件夹里的任何东西、开发 agent 的任何请求，都不影响外部程序交出去的值。
- 每次运行的记录里都有当时交出去的全部设置（`solver_settings`），报告据此写明。
- 它们不随划分一起锁定：研究员可以改，改动和其他配置改动一样写进记录（见 2.7）。一场考试内部不会变：所有对比对象用同一份设置，中断的考试只在场景目录没有变化时才能继续。
- 外部程序不知道这些设置是什么意思。让它们真正起作用，是运行命令的事（见 3.2）。

### 2.11 exam

最终考试的设置。六个键都必须写。

| 键 | 含义 | 值 |
|---|---|---|
| `compare` | 和谁对比。名字到 harness 文件夹的对应，文件夹相对场景目录，必须在场景目录里面。交付的 harness 总是参加，名字固定为 `delivered`，不用写、也不能用作别的对象的名字 | 对象，可以为空 |
| `repeats` | 每个对比对象在每道考试题上跑几次 | 正整数 |
| `aggregate` | 一个对比对象的全部计入分数怎样汇总成一个数 | `mean`、`median`、`min`、`max`、`sum` 之一 |
| `failure_score` | 一次运行没有得到官方分数、又不符合无效条件时，按多少分计入 | 数 |
| `invalid_reruns` | 一次运行符合无效条件时，最多重跑几次 | 整数，0 或更大 |
| `uses` | 考试题可以使用几次：在一个状态目录里最多举行几场考试 | 正整数 |

说明：

- 对比对象的文件夹在考试开始时才读取，要求和初始 harness 相同（有可执行的 `start`）。想和通用 agent 原样对比，就把 `initial_harness` 的路径再写一遍。文件夹可以在开发结束之后才放进场景目录，例如「通用 agent 直接拿到材料文件夹」这个对比对象。
- 名字的写法与题目编号相同。
- 一场考试 = 每个对比对象 × 每道考试题 × `repeats` 次运行；无效运行的重跑不另算一场。考试怎样进行见第 6 节。
- `uses` 可以由研究员改大，改动写进记录。

## 3. 三条命令

### 3.1 共同的约定

- 输入全部通过环境变量传入，名字都以 `HB_` 开头。外部程序自己环境里已有的 `HB_` 变量不会传下去；其他环境变量照常传下去。
- 所有路径都是绝对路径。`HB_SCENARIO` 是场景目录。
- 命令的标准输出和标准错误由外部程序原样存成文件。
- 退出码原样记录。外部程序不解读输出内容。
- 超时由外部程序执行：先给命令的整个进程组发 SIGTERM，等一小段时间后发 SIGKILL。命令正常退出后，它留在进程组里的其他进程也会被结束。容器不在这个进程组里，场景的命令要自己保证在被结束时收掉自己起的容器。

### 3.2 运行命令 `run`

在一道题的环境里，用一个 harness 文件夹的启动命令跑一遍，把产出和日志写进输出目录。

| 变量 | 含义 |
|---|---|
| `HB_TASK` | 题目编号 |
| `HB_HARNESS` | harness 文件夹。应以只读方式放进题目环境 |
| `HB_OUT` | 输出目录，已存在且为空 |
| `HB_MODEL_URL` | 模型出口的地址，形如 `http://<url_host>:<端口>`，不带路径。Anthropic 式客户端请求 `/v1/messages`，OpenAI 式请求 `/v1/chat/completions` |
| `HB_MODEL_KEY` | 这次运行的凭据 |
| `HB_MODEL` | 做题模型的名字 |
| `HB_SETTING_<名字>` | 研究员固定的做题设置，`solver_settings` 里每项一个；没有配置时一个也没有 |
| `HB_SECONDS` | 这次运行命令的时限（秒）：`limits.run_seconds`，或开发 agent 要求的更短的值。不限时没有这个变量。运行命令可以据此在被外部程序结束之前自己让 agent 停下、收好产出 |

要求：

- 在题目环境里执行 harness 文件夹里的 `start`，并把 `HB_MODEL_URL`、`HB_MODEL_KEY`、`HB_MODEL` 以同样的名字放进 `start` 的环境变量。
- 让 `HB_SETTING_*` 起作用，并且不让 harness 文件夹改掉它们。怎么做取决于 agent 产品，例如在调用产品的那一层把它们换成产品的参数。要注意：`start` 是 harness 文件夹自己的程序，只把设置放进 `start` 的环境变量并不能阻止它改写；设置要在 `start` 够不着的地方生效，或者由运行命令在运行结束后核对。外部程序这一侧保证的只有两件事：交给运行命令的值只来自 `scenario.json`，以及这些值写进了每次运行的记录。
- 把产出和日志写进 `HB_OUT`。`HB_OUT` 整个目录就是这次运行的产出，之后原样交给打分命令。
- 退出码 0 表示这次运行走完了；非 0 表示没走完。两种情况外部程序都会接着打分。

### 3.3 打分命令 `score`

对一份产出执行官方打分。

| 变量 | 含义 |
|---|---|
| `HB_TASK` | 题目编号 |
| `HB_PRODUCT` | 产出目录：某次运行的 `HB_OUT`，或开发 agent 自己构造的目录 |
| `HB_OUT` | 打分原始输出的目录，已存在且为空 |

要求：

- 不修改 `HB_PRODUCT`。
- 把官方打分的原始输出写进 `HB_OUT`，分数所在的位置与 `scenario.json` 的 `score` 一致。
- 退出码 0 表示打分完成（分数可以是任何值）；非 0 表示打分本身出错。

### 3.4 进入环境命令 `enter`

在一道题的环境里执行一条命令，不启动 agent。

| 输入 | 含义 |
|---|---|
| `HB_TASK` | 题目编号 |
| `HB_WORK` | 交换目录，已存在。开发 agent 通过它放进文件、取出结果 |
| 命令行参数 | 要执行的命令，接在 `commands.enter` 的参数后面 |

要求：

- 在题目环境里执行参数给出的命令，当前目录是交换目录在环境里的位置。
- 命令的输出直接写到标准输出和标准错误；退出码就是这条命令的退出码。

### 3.5 无效运行的判定命令 `invalid`（可选）

按研究员事先给的条件，判断一次运行本身是否无效、需要重跑。外部程序在每次运行打分之后执行它。

| 变量 | 含义 |
|---|---|
| `HB_TASK` | 题目编号 |
| `HB_RUN` | 这次运行的记录目录，只读。其中 `out/` 是运行的输出目录，`score/` 是打分的原始输出，`run.stdout`、`run.stderr`、`score.stdout`、`score.stderr` 是两条命令的输出，`usage.json` 是这次运行经模型出口的用量（见下） |

`usage.json` 的字段：`requests`、四种 token 计数和 `total_tokens`；`upstream_errors`（上游返回 429、5xx 或连不上的次数）；`refused`（被拒绝的请求数，按原因 `model` 或 `budget` 分）；`response_models`（响应里出现过的模型名）；`wait_seconds`（等上游开始回应的累计秒数）；`seconds`（请求的累计秒数）；`in_flight_at_close`（运行结束收回凭据时仍未完成的请求数，正常为 0；这些请求的用量计入开发预算，但不在这份记录里）；以及 `owner`、`pool`、`model`、`caps`。判定条件可以用这些字段，例如上游出错就算无效。

退出码：

- 0：有效。
- 10：无效，标准输出写原因。
- 其他、超时或无法启动：判定本身出错。记为判定出错，这次运行不算无效。

没有配置这条命令时，所有运行都不算无效。

## 4. harness 文件夹

方法对它只有两条硬性要求：

- 根目录下有一个可执行文件 `start`，即启动命令。运行命令在题目环境里执行它。
- 根目录下有一份清单 `MANIFEST.md`：文件夹里有哪些部分，每部分做什么、为什么加、去掉会怎样。初始 harness 可以没有清单，交付的版本必须有：开发 agent 指定交付时检查一次，交付检查时再查一次（不能缺，不能是空的）。

其余结构不规定。

## 5. 交付检查

开发 agent 最后一次用 `hb deliver` 指定的版本就是交付的版本。研究员在主机上执行交付检查（第 8 节的 `deliver`），外部程序依次做三件事：

1. 看存着的这个版本：内容必须仍与它入库时的哈希一致，有可执行的 `start`，有非空的 `MANIFEST.md`。任何一条不满足，检查失败，不试跑。
2. 冻结：把版本号、文件夹的哈希、清单的哈希写进记录。此后考试只认哈希与此相同的文件夹。
3. 试跑一道练习题（默认是 `split.practice` 的第一道，可以另指定）：把这个版本复制到状态目录之外的一个新的临时目录，用这份副本、场景自己的 `limits.run_seconds` 和 `limits.run_budget` 跑一次并打分。试跑的模型用量记在单独的一项里，不占开发预算，所以开发预算用完之后也能试跑。

试跑的结果有三种：

| 结果 | 条件 |
|---|---|
| 通过 | 运行命令和打分命令都在时限内以退出码 0 结束。不看分数 |
| 不通过 | 其他情况（有一条命令超时或退出码非 0） |
| 无效 | 这次运行符合无效运行的判定条件。既不算通过也不算不通过，重新执行交付检查即可 |

不通过就是退回：结果和原因写进记录，开发 agent 在 `hb status` 里看到，试跑的完整记录在它的记录目录的 `trial/` 下；考试拒绝开始。如果还有预算和时间，继续开发、重新指定交付、再做检查。开发 agent 在通过之后又指定了别的版本，就要对新的版本重新检查。

「全新的环境」在外部程序这一侧指的是：文件夹是放在别处的一份新副本，输出目录是新的，凭据是新的。题目环境本身和每次运行一样由运行命令建立；运行命令不应让题目环境看到开发沙盒的工作区。

## 6. 最终考试

研究员在主机上执行第 8 节的 `exam`。考试开始的条件：

- 最后指定的交付版本已经通过交付检查；
- 存着的交付版本的哈希与冻结时相同；
- 已经举行的考试少于 `exam.uses` 场。

任何一条不满足，考试被拒绝，原因写进记录，不产生任何运行，也不算用掉一次。

考试怎样进行：

- 对比对象是交付的 harness（`delivered`）和 `exam.compare` 里的每个文件夹。对比文件夹在考试开始时存为 harness 的版本并记下哈希。
- 每个对比对象在每道考试题上跑 `repeats` 次，同时进行的运行不超过 `limits.parallel_runs` 个。
- 所有对象用同一条运行命令、同一条打分命令、同样的 `limits.run_seconds`、`limits.score_seconds`、`limits.run_budget`、同一个做题模型、同一份 `solver_settings`、同一个无效判定命令。考试的模型用量不占开发预算。
- 每次运行按下面三种情况之一记下：

| 记为 | 条件 | 怎样计入 |
|---|---|---|
| `scored` | 不符合无效条件；打分命令在时限内以退出码 0 结束，且 `score` 指定的位置是一个数 | 计入这个数。运行命令本身超时或退出码非 0 不影响，只要打出了分 |
| `no_score` | 不符合无效条件，但没有得到官方分数 | 计入 `failure_score` |
| `invalid` | 符合无效条件 | 不计入，重跑；重跑 `invalid_reruns` 次之后仍然无效，这一格留空 |

- 一个对象的汇总结果 = 对它全部计入的数做 `aggregate`。留空的格不参加汇总，在结果里逐个列出。全部留空时没有汇总结果。
- 这是外部程序唯一读分数的地方；原始打分输出照样完整保存。外部程序不比较对象之间的高低。

中断与继续：

- 考试中途被打断（程序被停、机器故障）后，再执行一次 `exam` 就从断点继续：已经完成的运行保留，不重跑，不算新的一场。
- 继续的条件是场景目录和开考时一样，各对比对象的文件夹哈希也没有变。条件不满足时拒绝继续，以免同一场考试的运行处在不同条件下。这时要么把场景目录恢复原样，要么用 `exam --close` 把这场考试按现状结束：没跑的格留空，报告里标明。按现状结束的考试仍算用掉一次。

考试结果不回流：

- 考试的全部记录在状态目录的 `exam/` 下，任何沙盒都不挂载它。
- 一个状态目录里一旦开始过考试，就不再受理开发会话、交付检查、材料和回答。想继续开发，要用新的状态目录，并且不能把考试结果作为材料带进去（规则 5）。

## 7. 报告

第 8 节的 `report` 生成 `<状态目录>/report/report.json` 和 `report.md`。报告只从记录里取数，每个数后面带着它所依据的记录的序号（`ledger/ledger.jsonl` 里的 `seq`），可以逐条核对。内容：

- 分数：每场考试里，每个对比对象在每道考试题、每次重复、每次尝试上的结果和官方分数；按 `aggregate` 得到的汇总结果，以及计入了几次、其中几次没有官方分数、哪些格留空。
- 花费：开发阶段的模型用量（开发 agent 自己的、它发起的运行的、合计）和开发时长；交付试跑的用量；考试时每个对象每次运行的时长和用量。只有请求数和 token 数，不折算成钱。
- 开发过程：会话数、运行数、被拒绝和被打断的运行数、打分次数、进入环境的次数、问题数、回答数、材料增加的次数、场景目录的每次变更（哪些配置键变了，限制从多少改到多少）、无效运行及其原因。
- 交付物：每次指定和每次交付检查的结果；通过检查的版本号、文件夹哈希、清单全文，以及存着的文件夹和清单现在是否仍与记录的哈希一致。
- 场景：场景目录的哈希、划分的哈希、两个模型、限制、`solver_settings`、考试设置。

报告不做任何判断，不做显著性检验。考试没有结束时，报告列出已有的运行，不给汇总结果。

## 8. 主机一侧的命令

沙盒里的 `hb` 是给开发 agent 用的。研究员在主机上用的是另一个入口，名字不同，免得混淆：

```
python -m harness_builder --scenario <场景目录> --state <状态目录> <命令> ...
```

把包安装之后，同一个入口也叫 `hb-host`。状态目录保存一次开发的全部记录，第一次使用时建立，不能放在场景目录里面。

| 命令 | 作用 |
|---|---|
| `develop [--sandbox container\|local] [--materials 目录]...` | 开始一个开发会话；再执行一次就是继续（开发 agent 的工作区和记录都在）。`--materials` 先把一个文件夹加进材料，内容相同的文件夹不会加第二次。`local` 没有隔离，只用于测试 |
| `questions` | 列出开发 agent 的问题和已有的回答 |
| `answer 问题编号 [回答] [--file 文件] [--by 谁]` | 回答一个问题；回答成为一份新材料 |
| `add-material 路径 [--note 说明]` | 往材料里加一个文件或文件夹 |
| `limits [键=JSON值]...` | 不带参数时显示限制；带参数时改写 `scenario.json` 里的限制并写进记录，例如 `limits run_seconds=1800 dev_seconds=null` |
| `stop` | 叫停正在进行的开发会话 |
| `status` | 目前记录里有什么 |
| `deliver [--task 题目]` | 交付检查（第 5 节） |
| `exam [--close]` | 最终考试，或继续被打断的那一场；`--close` 把被打断的那一场按现状结束（第 6 节） |
| `report` | 生成并显示报告（第 7 节） |
| `verify` | 核对总记录、材料和 harness 各版本有没有被改过 |

退出码：0 表示完成，1 表示被拒绝或没有通过，2 表示用法错误。

说明：

- 开发会话进行时，`questions`、`answer`、`add-material`、`limits`、`status`、`stop` 在另一个终端里执行。开发会话、交付检查、考试三者同一时间只能进行一个。
- 改动的限制从下一个开发会话开始生效；正在进行的会话沿用它开始时的限制。要立即生效，先 `stop` 再 `develop`。
- `stop` 之后不再受理新的请求；已经在跑的运行跑完并记录，然后会话结束。
- 材料和回答的提供者不得接触过考试题的内容、答案或考试结果（规则 5）。这一条靠人遵守，程序只能做到开过考试之后不再收。
- 模型出口的请求日志在 `<状态目录>/model-requests.jsonl`。
